1. Fundamentos

Una base de datos es una colección organizada de datos que persiste en disco y se puede consultar y modificar de forma segura. El SGBD (sistema gestor, como PostgreSQL, MySQL o MongoDB) es el programa que la administra: guarda, protege, controla accesos y responde consultas. El esquema es la estructura (tablas, tipos, relaciones); la instancia son los datos guardados en un momento dado.

Una tabla es un conjunto de filas

Analogía: la lista de invitados de una fiesta. Nadie aparece dos veces, el orden no importa y cada persona está o no está en la lista.

Formalmente, cada columna tiene un dominio (el conjunto de valores posibles). El producto cartesiano de los dominios contiene todas las combinaciones imaginables, y la tabla es el subconjunto de las combinaciones que realmente existen: R ⊆ D₁ × D₂ × … × Dₙ.

D_nombre = {Ana, Beto}      D_ciudad = {Bogotá, Cali}
cliente  = {(Ana, Bogotá), (Beto, Cali)}   ⊆   D_nombre × D_ciudad

Conjunto frente a multiconjunto. Una tabla sin clave primaria puede repetir filas y entonces es un multiconjunto (una bolsa de canicas, donde importa cuántas hay). La clave primaria la convierte en un conjunto verdadero, y SELECT DISTINCT convierte cualquier resultado en un conjunto.

Ejercicio: razona con conjuntos

Clientes C = {Ana, Beto, Carla}; el cliente de cada pedido es la lista P = (Ana, Ana, Beto). a) ¿Qué devuelve SELECT DISTINCT cliente FROM pedido? b) ¿Qué clientes no tienen pedidos? c) ¿Cuántas filas da cliente CROSS JOIN pedido?

Solución: a) {Ana, Beto}, porque DISTINCT convierte la lista en conjunto. b) C − {Ana, Beto} = {Carla}: SELECT nombre FROM cliente EXCEPT SELECT cliente FROM pedido. c) |C| × |P| = 3 × 3 = 9 filas.

Cálculo relacional: describir el conjunto en vez de construirlo

El álgebra da una receta (qué operaciones aplicar y en qué orden). El cálculo solo declara qué propiedad cumplen las filas, igual que la notación de conjuntos {x | P(x)}. En el cálculo de tuplas las variables recorren filas; en el de dominios, valores de columnas.

-- Tuplas: clientes de Cali
{ t | t ∈ cliente ∧ t.ciudad = 'Cali' }
SELECT * FROM cliente WHERE ciudad = 'Cali';

-- Existencial: clientes con algún pedido
{ t | t ∈ cliente ∧ ∃p ∈ pedido ( p.cliente_id = t.id ) }
SELECT * FROM cliente c WHERE EXISTS (SELECT 1 FROM pedido p WHERE p.cliente_id = c.id);

-- Universal: clientes cuyos pedidos son todos mayores a 50
{ t | t ∈ cliente ∧ ∀p ∈ pedido ( p.cliente_id = t.id → p.total > 50 ) }
SELECT * FROM cliente c WHERE NOT EXISTS (SELECT 1 FROM pedido p WHERE p.cliente_id = c.id AND p.total <= 50);

-- Dominios: variables sobre valores, no sobre filas
{ <n> | ∃id, c ( cliente(id, n, c) ∧ c = 'Cali' ) }
LógicaSQL
∧ · ∨ · ¬AND · OR · NOT
∃ (existe)EXISTS
∀ (para todo)NOT EXISTS ... NOT (no existe un contraejemplo)

Teorema de Codd: el álgebra relacional y el cálculo relacional seguro (el que siempre devuelve un conjunto finito) tienen el mismo poder expresivo. Por eso el motor puede traducir tu consulta declarativa a un plan de operadores. SQL toma ideas de ambos: se parece al cálculo de tuplas al escribirlo (EXISTS, variables de fila) y se ejecuta como álgebra.

2. Modelo relacional y diagramas ER

Una tabla (entidad) tiene columnas (atributos) y filas (registros). La clave primaria (PK) identifica cada fila de forma única. La clave foránea (FK) apunta a la PK de otra tabla y garantiza integridad referencial. Las relaciones pueden ser 1:1, 1:N o N:M (esta última se resuelve con una tabla intermedia).

Tip. Cada FK va en el lado «muchos» de la relación: el pedido guarda el cliente_id, no al revés.
Ejercicio: modela una biblioteca

Un socio presta varios libros; un libro tiene varios autores.
Solución: tablas socio, libro, autor, prestamo (FK socio_id, FK libro_id, fecha) y libro_autor (FK libro_id, FK autor_id) para el N:M.

2b. Diseño: ER completo y teoría de dependencias

Modelo ER: entidades débiles y participación

Una entidad fuerte se identifica por sí sola; una débil no tiene clave propia y depende de un dueño (un dependiente solo existe como dependiente de un empleado). Tipos de atributo: simple, compuesto (dirección = calle + ciudad), multivaluado (varios teléfonos), derivado (edad se calcula desde la fecha de nacimiento) y clave. Participación: total (todo empleado pertenece a un departamento) o parcial.

ER extendido: generalización, especialización y agregación

Especialización (de arriba abajo): de persona nacen subtipos con atributos propios. Generalización (de abajo arriba): detectas lo común entre entidades y lo subes a un supertipo. Las restricciones son disjunta o solapada (una persona puede ser estudiante y profesor) y total o parcial. La agregación trata una relación como si fuera una entidad para poder relacionarla con otra. Una relación recursiva relaciona una entidad consigo misma (empleado supervisa empleado).

Las reglas de Codd

Codd definió una regla 0 y doce reglas para que un sistema sea realmente relacional: información en tablas, acceso garantizado por tabla-clave-columna, tratamiento sistemático de NULL, catálogo consultable con el mismo lenguaje, un sublenguaje completo, vistas actualizables, operaciones sobre conjuntos, independencia física, lógica, de integridad y de distribución, y no subversión (ningún acceso de bajo nivel salta las reglas). Ningún motor las cumple al 100%.

Superclave y claves candidatas

Una superclave es cualquier conjunto de columnas que identifica una fila de forma única; una clave candidata es una superclave mínima (si quitas una columna, deja de serlo). Si R(A,B,C,D) tiene como única candidata a A, toda combinación que incluya A es superclave: 23 = 8 superclaves.

Cierre de atributos, paso a paso

El cierre X+ es el conjunto de atributos que X determina. Se parte de X y se agrega el lado derecho de toda dependencia cuyo lado izquierdo ya esté contenido, hasta que no cambie (un punto fijo). Si X+ contiene todos los atributos, X es superclave.

R(A,B,C,D,E)    F = { A → B,  B → C,  CD → E }
(A)+  : {A} → A→B agrega B → B→C agrega C → {A,B,C}          no alcanza
(AD)+ : {A,D} → B → C → con C y D, CD→E agrega E → {A,B,C,D,E}   todos
AD es clave candidata: ni A ni D solos alcanzan.

Equivalencia de conjuntos de dependencias y cobertura canónica

F ≡ G si cada dependencia de G se deduce de F y viceversa. Ejemplo: F = {A→B, B→C, A→C} y G = {A→B, B→C} son equivalentes porque en G, (A)+ = {A,B,C} ya incluye C.

La cobertura canónica es la versión mínima equivalente. Pasos: 1) lado derecho de un solo atributo; 2) quitar atributos sobrantes del lado izquierdo; 3) quitar dependencias redundantes.

F = { A → BC,  B → C,  A → B,  AB → C }
1) Separar:   A→B, A→C, B→C, A→B, AB→C
2) AB→C: B→C ya existe, así que A sobra → B→C (repetida)
3) A→C se deduce de A→B y B→C (transitividad) → se elimina
Cobertura canónica:  Fc = { A → B,  B → C }

Cómo hallar la forma normal más alta

1) Halla las claves candidatas con cierres. 2) Marca los atributos primos (los que están en alguna clave). 3) Revisa cada dependencia X → Y: si X es superclave, cumple todo; si Y es primo, cumple 3FN pero no BCNF; si X es parte propia de una clave y Y no es primo, viola 2FN.

R(A,B,C)   F = { AB → C,  C → B }
Claves: AB (AB→C) y AC (AC→B por C→B). Primos: A, B, C
AB → C: AB es superclave            ✓
C → B : C no es superclave → viola BCNF; B es primo → cumple 3FN
Forma normal más alta: 3FN

Descomposición sin pérdida y que preserva dependencias

Una descomposición R → R1, R2 es sin pérdida si R1 ∩ R2 es clave de R1 o de R2: al unirlas no sobran ni faltan filas. Preserva dependencias si cada dependencia original se puede comprobar dentro de una sola tabla, sin hacer JOIN.

R(A,B,C)  F = { AB → C, C → B }     BCNF: R1(C,B)  R2(A,C)
R1 ∩ R2 = {C}, y C es clave de R1  →  sin pérdida ✓
AB → C ya no cabe en ninguna tabla  →  no preserva dependencias ✗
3FN siempre se logra sin pérdida y preservando; BCNF solo garantiza lo primero.

Forma normal dominio-clave (DKNF): toda restricción es consecuencia de restricciones de dominio y de clave. Es la forma más fuerte en teoría (implica BCNF, 4FN y 5FN), pero rara vez se logra en la práctica.

2c. Claves a fondo: superclave, candidata y primaria

La idea en una frase

Una superclave es un conjunto de una o más columnas cuyos valores bastan para distinguir cualquier fila de todas las demás. Analogía: en una biblioteca, la cédula identifica a cada socio. También lo identifica «cédula + color de camisa», porque la cédula ya bastaba y lo demás sobra. Las dos combinaciones son superclaves; solo la primera es mínima.

Qué la identifica: tres formas de decir lo mismo

EnfoqueEnunciadoCómo se prueba
Por filasK es superclave si para dos filas distintas t₁ ≠ t₂ siempre t₁[K] ≠ t₂[K]Buscar duplicados en las columnas de K
Por dependenciasK → R: K determina todas las columnasCierre: K+ = R
Por conjuntosLa proyección de R sobre K tiene tantos elementos como R: |πK(R)| = |R|COUNT(DISTINCT K) = COUNT(*)

K puede ser una sola columna o varias. Y atención: las claves son una propiedad del esquema (de las reglas del negocio), no de los datos que hoy hay en la tabla.

La familia de claves

TérminoDefinición
SuperclaveCualquier conjunto de columnas que identifica cada fila
Clave candidataSuperclave mínima: si le quitas cualquier columna, deja de identificar
Clave primariaLa candidata que eliges como identificador oficial (sin NULL)
Clave alternaLas candidatas no elegidas; se declaran UNIQUE NOT NULL
Atributo primoColumna que pertenece a alguna clave candidata (no primo: a ninguna)
CompuestaClave de más de una columna
Natural / subrogadaDato del mundo real (cédula) / número artificial sin significado (id)

Propiedad clave (monotonía): si K es superclave, cualquier superconjunto K ∪ X también lo es. Agregar columnas nunca destruye la identificación. Por eso hay muchas superclaves y por eso solo nos interesan las mínimas.

Cómo obtener las claves candidatas: algoritmo con cierres

Cuando tienes las dependencias funcionales y no es evidente cuál es la clave:

  1. Columnas indispensables: las que nunca aparecen a la derecha de una dependencia. Nadie las determina, así que están en toda clave.
  2. Columnas descartadas: las que solo aparecen a la derecha. Otras columnas las determinan, así que no están en ninguna clave.
  3. Calcula el cierre de las indispensables. Si es todo R, esa es la única clave.
  4. Si no, agrega las columnas «intermedias» (las que aparecen a ambos lados) de a una, luego de a dos, etc., y salta cualquier conjunto que contenga una clave ya hallada.
  5. Verifica la minimalidad: quita cada columna de la clave y comprueba que el cierre ya no sea R.

Ejemplo A: una sola clave. R(est, curso, prof, aula, nota) con las reglas: (est, curso) → nota; curso → prof; prof → aula.

1) Derechas: nota, prof, aula.   Izquierdas: est, curso, prof.
   Nunca a la derecha:  est, curso  → indispensables
   Solo a la derecha:   nota, aula  → en ninguna clave
   Intermedia:          prof
2) {est, curso}+ :  {est, curso}
                    (est,curso)→nota  agrega nota
                    curso→prof        agrega prof
                    prof→aula         agrega aula     = {est,curso,prof,aula,nota} = R  ✓
3) Minimalidad:  {est}+ = {est}    {curso}+ = {curso, prof, aula}   ninguna alcanza
Resultado: única clave candidata = {est, curso}

Todas las superclaves son {est, curso} más cualquier subconjunto de {prof, aula, nota}: 23 = 8.

{est,curso}              {est,curso,prof}          {est,curso,aula}          {est,curso,nota}
{est,curso,prof,aula}    {est,curso,prof,nota}     {est,curso,aula,nota}     {est,curso,prof,aula,nota}

Ejemplo B: varias claves. R(A,B,C) con AB → C y C → B.

Nunca a la derecha: A  → indispensable.   {A}+ = {A}  no alcanza
Intermedias: B, C (aparecen a ambos lados). Probar de a una:
  {A,B}+ = {A,B} → AB→C agrega C = R  ✓  clave
  {A,C}+ = {A,C} → C→B agrega B = R  ✓  clave
  {A,B,C} contiene claves → se salta
Claves candidatas: AB y AC.   Superclaves: AB, AC, ABC.   Atributos primos: A, B, C

Clave compuesta y foránea en el mismo caso

CREATE TABLE inscripcion (

Cada columna de la PK es a la vez una clave foránea que apunta a la clave primaria de otra tabla. La PK compuesta impide inscribir dos veces al mismo estudiante en el mismo curso.

Errores frecuentes. 1) Llamar clave a un conjunto que solo es único hoy. 2) Usar como PK un dato que cambia (email, nombre). 3) Olvidar UNIQUE en las claves alternas, con lo que se cuelan duplicados. 4) PK compuestas de 4 o más columnas: mejor un id subrogado con UNIQUE sobre la combinación. 5) Permitir NULL en una columna que forma parte de la clave primaria.
Ejercicio 1: una cadena de dependencias

R(A,B,C,D) con A → B, B → C, C → D. Halla la clave y cuenta las superclaves.

Solución: A nunca está a la derecha, así que es indispensable. {A}+ = {A,B,C,D} = R, entonces la única clave es {A}. Superclaves: A más cualquier subconjunto de {B,C,D}: 23 = 8.

Ejercicio 2: varias claves

R(A,B,C,D) con AB → C, C → D, D → A. Halla todas las claves candidatas y las superclaves.

Solución: B nunca está a la derecha, así que está en toda clave; {B}+ = {B}. Pruebas: {A,B}+ = {A,B,C,D} ✓; {B,C}+: C→D, D→A, y AB→C, todo ✓; {B,D}+: D→A, AB→C, todo ✓. Claves candidatas: AB, BC, BD. Superclaves: todos los conjuntos con B y al menos una de A, C, D: 23 − 1 = 7 (AB, BC, BD, ABC, ABD, BCD, ABCD).

Visto como conjuntos. Que K sea superclave significa que la función que a cada fila le asigna sus valores en K es inyectiva: no hay dos filas con la misma imagen. Por eso |πK(R)| = |R|. Las superclaves forman una familia cerrada hacia arriba (si K lo es, también K ∪ X) y las candidatas son sus elementos minimales.

CTE recursiva: recorrer jerarquías

Sirve para árboles y grafos (organigramas, categorías, rutas). Tiene una parte ancla (el punto de partida) y una parte recursiva que se repite hasta que no aparecen filas nuevas. Analogía: un árbol genealógico leyendo generación por generación.

Ancla: la gerente general (nivel 1)Paso 1: sus directos (nivel 2)Paso 2: los directos de ellos (nivel 3)Sin filas nuevas: termina
WITH RECURSIVE jerarquia AS (
  SELECT id, nombre, jefe_id, 1 AS nivel FROM empleado WHERE jefe_id IS NULL      -- ancla
  UNION ALL
  SELECT e.id, e.nombre, e.jefe_id, j.nivel + 1
  FROM empleado e JOIN jerarquia j ON e.jefe_id = j.id                           -- paso recursivo
)
SELECT * FROM jerarquia ORDER BY nivel;
Visto como conjuntos. La recursión calcula una clausura transitiva: se agregan conjuntos de filas hasta alcanzar un punto fijo en el que ya no cambia nada. Un ciclo en los datos la haría infinita, así que limita el nivel (WHERE nivel < 20).

Código guardado dentro de la base de datos. Una función devuelve un valor y se usa dentro de un SELECT; un procedimiento ejecuta acciones, puede controlar transacciones y se invoca con CALL.

CREATE FUNCTION total_cliente(p_id INT) RETURNS NUMERIC AS $$
  SELECT COALESCE(SUM(total), 0) FROM pedido WHERE cliente_id = p_id;
$$ LANGUAGE sql;
SELECT nombre, total_cliente(id) FROM cliente;

CREATE PROCEDURE transferir(origen INT, destino INT, monto NUMERIC)
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE cuenta SET saldo = saldo - monto WHERE id = origen;
  UPDATE cuenta SET saldo = saldo + monto WHERE id = destino;
END $$;
CALL transferir(1, 2, 100);

Ventajas: la lógica vive junto a los datos, hay menos viajes por la red y se controla con permisos (GRANT EXECUTE). Costos: es más difícil de versionar, probar y migrar entre motores.

Triggers (disparadores)

Un trigger ejecuta una función automáticamente cuando ocurre un INSERT, UPDATE o DELETE. Es como un sensor de movimiento que enciende la luz sin que nadie la toque. Dentro, NEW es la fila nueva y OLD la anterior.

BEGIN
  INSERT INTO auditoria (tabla, operacion, fecha) VALUES (TG_TABLE_NAME, TG_OP, now());

Cursores

Un cursor recorre un resultado fila a fila o por lotes, como un marcapáginas. Útil para procesar millones de filas sin cargarlas todas en memoria.

BEGIN;
DECLARE c CURSOR FOR SELECT id, nombre FROM cliente ORDER BY id;
FETCH 100 FROM c;      -- primeras 100 filas
FETCH 100 FROM c;      -- las 100 siguientes
CLOSE c;
COMMIT;
Regla. SQL está pensado para trabajar con conjuntos completos. Una sola sentencia UPDATE suele ser mucho más rápida que un cursor que actualiza fila por fila; usa cursores solo cuando no haya alternativa.

PIVOT y UNPIVOT

Pivot convierte valores de filas en columnas; unpivot hace lo contrario.

  SUM(total) FILTER (WHERE EXTRACT(MONTH FROM creado) = 1) AS ene,
  SUM(total) FILTER (WHERE EXTRACT(MONTH FROM creado) = 2) AS feb

SELECT cliente_id, 'ene' AS mes, ene AS total FROM resumen
UNION ALL
SELECT cliente_id, 'feb', feb FROM resumen;

5. Normalización


Normalizar es organizar las tablas para eliminar redundancia y evitar anomalías al insertar, actualizar o borrar.


1FN: cada celda guarda un solo valor (nada de «tel1, tel2» ni listas en una columna). 2FN: cumple 1FN y cada columna depende de toda la clave, no de una parte. 3FN: cumple 2FN y ninguna columna depende de otra columna que no sea la clave.

Problemas: «producto» guarda una lista (viola 1FN) y «ciudad» depende de «cliente» (viola 3FN). Se separa en cliente(id, nombre, ciudad), pedido(id, cliente_id) y detalle_pedido(pedido_id, producto_id).


Tip. Normaliza hasta 3FN por defecto y desnormaliza solo con una razón medida, por ejemplo reportes lentos.

Base teórica: dependencias funcionales
Decimos que A → B cuando el valor de A determina un único valor de B. Ejemplo: cliente_id → ciudad. Toda la normalización consiste en que cada dato dependa de «la clave, toda la clave y nada más que la clave».

  • Actualización: si Ana cambia de ciudad y la ciudad está repetida en 50 filas, olvidar una deja datos contradictorios.
  • Borrado: al eliminar el único pedido de Beto desaparece también su ciudad.

BCNF y formas superiores
BCNF: todo determinante (lo que está a la izquierda de una dependencia) debe ser clave candidata. Caso típico: clase(alumno, materia, profesor) donde cada profesor da una sola materia (profesor → materia). Cumple 3FN pero no BCNF; se separa en profesor(profesor, materia) e inscripcion(alumno, profesor).
4FN: elimina dependencias multivaluadas (un empleado con varias habilidades e idiomas independientes no debe cruzarse en una sola tabla). 5FN: elimina dependencias de reunión; es muy rara en la práctica.
0FN: listas y repetidos1FN: valores atómicos2FN: sin parciales3FN: sin transitivasBCNF: determinantes = claves


Cuándo desnormalizar
Solo con una medición que lo justifique: reportes que unen muchas tablas, contadores precalculados (pedido.total) o tablas de consulta de solo lectura. A cambio, tú mantienes la coherencia con triggers o procesos.
Tip. Prueba rápida de 3FN: por cada columna no clave pregunta «¿qué la determina?». Si la respuesta es otra columna no clave, sepárala.

6. Transacciones e índices


Una transacción agrupa operaciones que se ejecutan todas o ninguna. Se rige por ACID: Atomicidad (todo o nada), Consistencia (respeta las reglas), Aislamiento (transacciones simultáneas no se estorban) y Durabilidad (lo confirmado sobrevive a una caída).


BEGIN;
UPDATE cuenta SET saldo = saldo - 100 WHERE id = 1;
UPDATE cuenta SET saldo = saldo + 100 WHERE id = 2;
COMMIT;  -- o ROLLBACK; si algo falla


Un índice es una estructura (normalmente un árbol B) que acelera búsquedas a costa de espacio y de escrituras más lentas.


CREATE INDEX idx_pedido_cliente ON pedido (cliente_id);
EXPLAIN ANALYZE SELECT * FROM pedido WHERE cliente_id = 7;


Tip. En EXPLAIN, «Seq Scan» sobre una tabla grande suele indicar que falta un índice. Indexa columnas de FK y de filtros frecuentes, no todas.


Ejercicio
Una transferencia descuenta de A pero el servidor cae antes de abonar a B. ¿Qué propiedad lo protege?
Solución: la atomicidad: sin COMMIT, el descuento se revierte.

ROLLBACK;   -- ambos saldos vuelven a 500 y 200

-- Deadlock: se cruzan dos transacciones
t1  A: UPDATE cuenta SET saldo = saldo - 10 WHERE id = 1;   (A bloquea la fila 1)
t2  B: UPDATE cuenta SET saldo = saldo - 10 WHERE id = 2;   (B bloquea la fila 2)
t3  A: UPDATE cuenta SET saldo = saldo + 10 WHERE id = 2;   (A espera a B)
t4  B: UPDATE cuenta SET saldo = saldo + 10 WHERE id = 1;   (B espera a A) → deadlock

Patrón de la aplicación. Mantén las transacciones cortas, sin esperar al usuario dentro de ellas, y reintenta (3 veces como máximo) ante errores de deadlock o de serialización.
Qué nivel usar. READ COMMITTED para la mayoría de aplicaciones; REPEATABLE READ para reportes que deben ver datos coherentes; SERIALIZABLE para lógica financiera crítica, aceptando reintentos.


Índices a fondo: cómo funciona un B-tree
Sin índice, el motor lee la tabla completa fila por fila (full scan). Un índice B-tree es un árbol ordenado: cada nodo guía hacia el rango correcto y las hojas apuntan a la fila real.
Con 1.000.000 de filas, un B-tree real tiene unos 3 o 4 niveles: se leen 4 páginas en vez de miles. La búsqueda cuesta O(log n); recorrer toda la tabla cuesta O(n).

6b. Concurrencia y recuperación a fondo


Schedules y serializabilidad
Un schedule es el orden en que se intercalan las operaciones de varias transacciones. Es serial si van una tras otra, y serializable si equivale a algún orden serial. Dos operaciones entran en conflicto si son de transacciones distintas, tocan el mismo dato y al menos una escribe. Para probar la serializabilidad por conflictos se dibuja el grafo de precedencia: un nodo por transacción y una flecha Ti → Tj si una operación de Ti en conflicto ocurre antes que una de Tj. Sin ciclos = serializable.
S1: R1(A) W1(A) R2(A) W2(A) R1(B) W1(B)
    W1(A) precede a R2(A): T1→T2. No hay flecha de vuelta → serializable (equivale a T1, T2)
S2: R1(A) R2(A) W1(A) W2(A)
    R1(A) antes de W2(A): T1→T2.  R2(A) antes de W1(A): T2→T1  → ciclo → NO serializable (actualización perdida)
RecuperabilidadRegla
RecuperableSi T2 lee lo que escribió T1, T2 no confirma antes que T1
Sin cascadaSolo se leen datos ya confirmados
EstrictoTampoco se escribe sobre datos no confirmados


Protocolos de control de concurrencia
Bloqueo en dos fases (2PL): cada transacción primero solo adquiere bloqueos (fase de crecimiento) y después solo los libera (fase de encogimiento); una vez que libera uno, no puede pedir otro. Garantiza serializabilidad. 2PL estricto: mantiene los bloqueos exclusivos hasta el COMMIT, así evita lecturas sucias y cascadas.
BEGINCrece: adquiere bloqueosPunto de bloqueo (tiene todos)Encoge: liberaCOMMIT
Protocolo de grafo (de árbol): los datos se organizan en árbol y se bloquea bajando de padre a hijo; no produce deadlocks, pero exige conocer el orden de acceso.
Bloqueo de granularidad múltiple: se puede bloquear la base, una tabla, una página o una fila. Para bloquear una fila, antes se toman bloqueos de intención (IS, IX, SIX) en los niveles superiores y así otra transacción sabe qué hay abajo.
Compatibles (sí) / no (no)    IS   IX   S    SIX  X
IS                              sí   sí   sí   sí   no
IX                              sí   sí   no   no   no
S                               sí   no   sí   no   no
SIX                             sí   no   no   no   no
X                               no   no   no   no   no
Ordenamiento por marcas de tiempo: cada transacción recibe una marca TS al empezar y cada dato guarda la marca de su última lectura (R-TS) y escritura (W-TS). Si T lee y TS(T) < W-TS, se aborta (leería el futuro). Si T escribe y TS(T) < R-TS, se aborta. Si TS(T) < W-TS, se aborta, o con la regla de escritura de Thomas se ignora esa escritura obsoleta. No hay deadlocks, pero sí abortos.


Prevención y detección de deadlocks
EsquemaSi T1 pide un bloqueo que tiene T2
Wait-dieT1 más vieja espera; T1 más joven muere (aborta y reintenta con la misma marca)
Wound-waitT1 más vieja hiere a T2 (la aborta); T1 más joven espera
DetecciónGrafo de espera: Ti → Tj si Ti espera a Tj. Un ciclo es un deadlock y se aborta una víctima, normalmente la de menor costo


Recuperación basada en log
El log guarda registros de inicio, de cada cambio (con valor viejo y nuevo) y de commit. Regla WAL: el log se escribe en disco antes que los datos. Con modificación diferida se aplica el cambio solo al confirmar (basta REDO); con modificación inmediata se aplica en cuanto ocurre (hace falta UNDO y REDO). Un checkpoint marca un punto desde el cual no hay que revisar el log anterior. Los motores modernos usan el algoritmo ARIES: análisis, redo y undo.
<T1 start>
<T1, A, 500, 400>       (transacción, dato, valor viejo, valor nuevo)
<T1 commit>
<T2 start>
<T2, B, 200, 300>
--- caída del servidor ---
T1 tiene commit → REDO: A = 400.   T2 no lo tiene → UNDO: B = 200.
Alternativa histórica: shadow paging, que mantiene una copia de la tabla de páginas y la cambia de golpe al confirmar.

B-tree frente a B+ tree
En el B-tree los datos pueden estar en cualquier nodo. En el B+ tree solo las hojas guardan los datos o punteros y están enlazadas, así los rangos se recorren en orden y los nodos internos (que solo guían) caben más claves y el árbol es más bajo. El diagrama del módulo 6 es un B+ tree. El orden m es el máximo de hijos por nodo (m−1 claves).
Orden 4 (máximo 3 claves por nodo). Insertar 10, 20, 30:  [10 20 30]
Insertar 40: no cabe → la hoja se divide  [10 20] ←→ [30 40]  y la clave 30 sube a la raíz [30]
Ejercicio: orden y altura
Página de 4096 B, clave de 12 B, puntero de 8 B. ¿Orden y altura para 1.000.000 de registros? Solución: 12(m−1) + 8m ≤ 4096 → 20m ≤ 4108 → m = 205. Altura ≈ log205(10⁶) ≈ 2,6 → 3 niveles.
